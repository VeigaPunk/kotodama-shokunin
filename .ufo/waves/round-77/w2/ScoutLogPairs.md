## 2. Why each invalidity is real

**D01–D10 (wiring defect, `fabricated-base-observation` class).** All ten
pairs share one `observe_cmd` —
`git -C . grep -c -E '^#' 211f9526…90c15 -- LOG.md` — whose real stdout is
`211f9526…90c15:LOG.md:149` (raw, exit 0, below). `parse ":([0-9]+)$"` → token
`149`. Every pair records `"observed_at_base": "1"`. `pair_problems` accepts a
recorded string at face value (accept-ca.py:1712–1714 checks only type), but
`leg_basemismatch` (accept-ca.py:1866–1872) compares the recorded lead token
to the live observation → `recorded-observed-at-base='1'!='149'` → `misses`
non-empty → BASEMISMATCH leg **fails**. The probe ledger frozen as-is yields
`red=11 green=[] unobservable=[]` but `unobserved/miss=[D01..D10]` →
`passed = False`. (The selftest names this exact class:
`fabricated-base-observation` sets `pairs[0]["observed_at_base"]="0"` and
expects red — the probe ships it unmarked.) `expected_after:"1"` on D01–D10 is
the same off-by-misreading (`149` was presumably counted on a `grep -c`
without rev, or hand-set).

**D11 (not red at base; circular self-observation).**
`stated_parse "Total knowledge entries: ([0-9]+)\."` on stated_text "Total
knowledge entries: 243." → stated token `243`. The observe grep
(`grep -o -E 'Total knowledge entries: [0-9]+' corpus/README.md`) emits **five
matches** (README has totals lines at 755/798/819/830/834); `parse
"entries: ([0-9]+)"` takes `re.search`'s first hit → observed token `243` ==
stated `243` → BASEMISMATCH `green=[D11]` → `passed = False`, and the kill
rule ("any ledger pair not red at base") fires. Worse, the pair is circular:
`observe_cmd` re-reads the very line the pair states, so it cannot register a
mismatch; the real footer truth at base is line 834, `Total knowledge
entries: 253.` — the 243 on :755 is a stale per-section total (cf.
LC77-C-05's case-drift sibling). `observed_at_base` is `null` (absent):
structurally tolerated by both checks, semantically consistent with the
author never having observed this pair. `expected_after:"244"` is also wrong
against any footer truth (claim C's after-state is 254), but that is
lands-domain, not a base-validity defect.

`--ledger-check` reproduces the staged receipt:
`python3 -B …/accept-ca.py --ledger-check …/probe-real-ledger.json --root
<lane> --base 211f9526… --work $S` → stdout `LEDGER-CHECK-77: PASS pairs=11`,
`exit=0`. Conclusion: the checker's "PASS" certifies *structural grammar only*
— both defect classes above pass through it to BASEMISMATCH, so the W1
report's "PASS pairs=11" is true but does not establish these are usable
candidates.

## 4. Implications for the L1

- Do not freeze this probe verbatim: a `ledger.json` containing D01–D10 as
  staged fails BASEMISMATCH on `unobserved/miss` ×10 and on `green=[D11]` —
  11 of 11 pairs dead, ≥10 red still satisfied but `not misses` fails.
- D01–D10 are salvageable by wiring: replace each `observed_at_base` with the
  real observed token `"149"` (the semantic mismatch stated≠observed stays
  genuine). No other field is defective.
- D11 is not salvageable by rewiring: its observation is self-referential
  (observes the line it asserts). A valid REPAIR pair needs a site whose
  stated claim is *false* at base (e.g. asserting the stale 243 *is* the
  footer total while observing line 834's 253), or an independent observation
  that can register mismatch.
- Checker gap worth routing: `pair_problems()`/`--ledger-check` should reject
  a recorded `observed_at_base` ≠ live observation and (for ANNOTATE at
  minimum) stated==observed, so "PASS pairs=N" actually certifies candidates.
