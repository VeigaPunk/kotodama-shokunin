# SentinelGuard — Claim O receipt_guard review

Axes: **coverage** (all receipt-bearing refs are seen), **operability** (Git/path failures remain fail-closed), **calibration** (reported hashes identify the actual source ref). Read-only review; no source edits or checks run. Initial review covered HEAD plus a branch selected from `symbolic-ref` (default `main` when detached), its `origin` ref, and tolerance of missing refs. The private clone matched baseline at that inspection; no changed patch was available then.

## Findings

1. **High — attached non-main branch can miss the required main refs.** If HEAD is attached to `refs/heads/feature`, a receipt present only on `refs/heads/main` or `refs/remotes/origin/main` is missed when probing only the symbolic branch and `origin/feature`; guard returns success and permits overwrite. The round-50 O contract explicitly names `main` and `origin/main` (`reports/round-50/claims.json:34-36`); the fleet audit reproduces the HEAD-below-tip false negative and recommends those exact refs (`JjAuditKotodama.md:104-127,220-224`). **Smallest fix:** always probe HEAD, `refs/heads/main`, and `refs/remotes/origin/main`, independent of attachment; optional attached-branch probes may be additive. **Fixture:** attached `feature` HEAD and `origin/feature` lacking the path, while main/origin-main contains it; expect exit 3 and the actual holding ref/hash in the diagnostic.

2. **Medium — do not confuse the receipt-holding commit with the landed tip.** A local `refs/heads/main` can contain the receipt while `origin/main` is behind and does not. The guard must still refuse, but printing the origin tip as `landed_sha` without labeling the holder ref/hash risks making it appear that the receipt itself is landed there. The motivating audit says local jj `HEAD` may be an empty commit not on either main ref, and cited hashes must be landed (`JjAuditKotodama.md:73-103`). **Smallest fix:** report separate `head_sha`, `holding_ref`/`holding_sha`, and (only as a separately labeled branch/remote tip) `landed_sha`; never use a remote tip as the receipt's holding hash unless that ref's tree was verified to contain it. **Fixture:** local main B has the receipt, origin main A does not, and jj HEAD C differs from both; expect refusal, `holding_ref=refs/heads/main` and holding SHA B, while any landed SHA is clearly identified as A and not as the receipt-bearing commit.

3. **Medium — missing-ref tolerance must not turn lookup failure into permission.** “Missing refs tolerated” is safe only for genuinely absent optional refs. A malformed/unresolvable ref or Git read failure must retain the existing fail-closed behavior. Also probe branch refs even if HEAD is unborn; do not early-return on `_head_commit()` returning `None` before checking main/origin-main. **Smallest fix:** distinguish absent from failed/unresolvable ref lookup and fail closed on the latter. **Fixtures:** absent main/origin refs with an unborn repository and a new receipt remain allowed; then add a valid origin/main receipt while HEAD remains unborn and expect refusal; corrupt/unresolvable a present ref and expect exit 3 (`RECEIPT-GUARD-GIT`). Existing fail-closed controls include missing Git and corrupt HEAD (`receipt_guard.py:296-297,331-342`).

Executor reported adding unconditional `main`/`origin/main` probes alongside the attached-branch probes and an attached-`feature` fixture. This addresses finding 1 by design; the patch and its test results are still pending.

Two proof obligations remain: (a) if only a local `refs/heads/*` contains the receipt, report that as `holding_ref`/`holding_sha` and do not call it `landed_sha` unless the term explicitly means an unpushed local branch; use `landed_sha=none` when no remote ref is verified to contain the receipt; (b) test a present-but-corrupt/unresolvable ref against the proposed `rev-parse` return-code handling. Tolerate only proven absence; if absence and corruption are indistinguishable at rc 1, use a stronger presence check and fail closed on ambiguity.
