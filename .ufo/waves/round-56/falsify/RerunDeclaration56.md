## Residual risk

- `check` cannot authenticate the hash: any well-formed 40-hex revision line satisfies it, and a hand-edited hash of a receipt whose commands were never run would pass. The binding to reality is `run` printing the resolved hash plus the receipts commit `456f5ad`; this is inherent to a post-hoc checker, not a break of the routed contract.
- `check` compares against the declarations of the checker's own lane worktree, not of the receipt's measured revision (I used exactly this parameterization for the round-55 control). If claims.json changes after a receipt is written, a valid old receipt can newly fail; the honest procedure for that is re-running `run --rev`.
- The command comparison is set-based: a receipt that dropped one of the two identical accept-c lines (counting or acceptance role) would still pass while losing a role's output. The round-56 receipt contains all six lines, so nothing in scope; noting the semantics only.
- `check` reads only the receipt and declarations; it does not verify the recorded outputs (exit codes, leg lines) against a fresh run. The counting-and-acceptance outputs are re-verifiable by `run --rev b4b7db9...` at any time.
