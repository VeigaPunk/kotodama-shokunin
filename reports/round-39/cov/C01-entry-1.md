## 3. The four legs — what "checked" means

An example counts as checked when all four legs pass at its class's obligations. A leg that cannot apply at that class is marked N/A *in the receipt with a reason*, never silently skipped (fail-closed, `verification-method-overview.md` §6).

| Leg | Question | Evidence recorded | Fail shape |
|---|---|---|---|
| Instantiate | does the example contain the structures the named rules govern? | rule ids → the example elements that realize them | the rules are named but nothing in the example exercises them (dead rules, §7 F5) |
| Derive | does each stated consequence hang on a named rule? | a consequence↔rule map, one row per stated consequence | a consequence traces to no rule id (F1), or to a rule outside the cited set (F2) |
| Reject | does the example (or its receipt) show the rules refusing something? | the control input, the rule that rejects it, the observed verdict | no control shown, or a "control" the rules could not possibly reject (F3, green-by-construction) |
| Label | is the example marked as what it is? | the verbatim label | invented example without NON-CANON; attested data presented as invention; invented example drifting into canon-voiced prose (F4) |

**The receipt** (what a passing audit records; borrow the row-by-row discipline of `pre-declared-hold-set-reconciliation.md:39`): entry and digest at check time; class; rules named (ids + line cites); the consequence↔rule map; controls run (input, rejecting rule, actual verdict); label check (verbatim); freshness basis (§6); findings with §7 class ids; auditor and date; re-audit trigger. A receipt is a **debt record**: it captures what was checked, it does not certify the example's content into any world (DR-WE-09).

## 5. Negative controls and mutation discipline

- **A negative control is an input the entry's rules forbid** — and the check shows the rule rejecting it. Reuse the overview's controls where they apply: an illegal name segment, a loan dated before contact, a swapped viewer, a removed material dependency (`verification-method-overview.md:161`).
- **Mutation discipline (the falsification question for the example itself):** change one rule the example names, and at least one stated consequence must change. If no consequence changes under any single-rule mutation, then either the example does not instantiate that rule (dead rule, F5) or the rule is idle decoration in the entry — either way it is a finding against the *entry*, not just the example. This is the design discipline mutation analysis imports (DeMillo/Lipton/Sayward 1978, **to-verify**): a test suite is measured by the mutants it kills, and a suite that kills none measures nothing.
- **A control that cannot fail is not a control.** If the rejecting condition is unreachable under the entry's own rules, the "control" is green by construction — the measured circularity mode of `verification-independence-anti-circularity.md:3`. Rewrite it so the rule could have accepted.
- **Keep the failing case on record.** Like the overview's release rule, failure evidence is not averaged away by passing siblings (`verification-method-overview.md` §6): the receipt stores the control's actual observed verdict, not the expectation that it would fail.
- **Regression leg:** a receipt may re-run a recorded control after edits instead of inventing a new one — that is `label-channel-routing-verification.md:82`'s step, generalized. Record which control was re-run and the observed verdict.

## 6. Freshness: a new derivation, not a restatement

- The partition's own rule: "Reproducing the author's worked example alone tests copying, not productivity" (`verification-method-overview.md:54`). An example audit therefore asks for **at least one input not present in the entry's own prose** for classes (c)–(e) — a new name, a new compound, a new boundary case — derived under the same rules. For class (b) micro-examples, freshness is satisfied by construction (the paragraph is itself a fresh culture), and the receipt records that basis.
- **Fresh, not adversarial.** The fresh input must be inside the rules' declared scope; a fresh input that violates scope is a negative control (§5), not evidence of productivity. Run both kinds.
- **Copying masquerading as freshness** — same derivation with relabeled nouns — is caught exactly by the derive leg: if the consequence↔rule map is identical after relabeling, nothing new was derived, and the receipt says so.

## 8. Calibration

- **The instructional-psychology literature is an analogy, not a foundation.** The worked-examples effect (Sweller 1988; Sweller & Cooper 1985; Renkl 2014 — all **to-verify**, none consulted this round) is a mainstream result about *learning from studied examples*; this entry borrows its design moral — examples teach when steps are explained and fail quietly when steps are unexplained — and applies it to *authoring auditable examples*. That transfer is this lane's analogy, flagged as such; nothing here asserts a finding of instructional psychology, and no cultural claim rests on it.
- **Mutation analysis is imported at analogy grade.** Its core discipline (a test's adequacy is measured by the mutants it detects) motivates §5's mutation test; the software-engineering result itself is **to-verify**, and no equivalence between corpus examples and program tests is claimed.
- **A passing example audit is a consistency result, never correctness or canon** — the same boundary as two-reader agreement (`two-reader-interop-agreement.md`) and the anti-laundering invariant (`verification-method-overview.md:206`). "The example checks out" means *the demonstration was performed as declared*, nothing more.
- **Pop-mythography guard** (`QUALITY.md` item 2): an example may *demonstrate* a contested framework (a monomyth-structured plot, a glottochronology date) only when the entry's calibration section has flagged the framework; the example cannot launder a flagged framework back into respectability by making it look vivid.

## 10. Applying it — build order, and a demonstration on a landed example

1. **Class** the example (§2) and record it.
2. **List the rules** the example names (or should name), by stable id and line.
3. **Map** every stated consequence to a rule id (the derive leg); mark F1/F2 rows.
4. **Mutation-test** one named rule (§5); record what changed.
5. **Run or locate** one negative control; record input, rejecting rule, observed verdict.
6. **Check the label** verbatim; record it.
7. **Freshness**: state the basis (fresh input, or by-construction for micro-examples).
8. **File findings** with §7 ids and path:line; hand them to the owner.
9. **Write the receipt**; set the re-audit trigger.
